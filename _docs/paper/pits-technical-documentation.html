1. Summary

PITS lets an authorised publisher register a PDF document and lets anyone, without logging in, check whether a document they hold is byte-for-byte identical to a registered one. The system computes the document’s SHA-256, stores it with registry metadata in PostgreSQL, and anchors the hash on an Ethereum-compatible blockchain by sending a transaction whose calldata is VALUE:<sha256>. Verification re-hashes the uploaded file, finds the registry record, reads the transaction back from the chain and compares.

Until October 2026 the chain was a local development ledger (Anvil, chain ID 31337). The system now supports any EVM chain through configuration and has been proven on Ethereum Sepolia (chain ID 11155111), where each anchor can be inspected independently on Etherscan.

Verified on a public chainCanonical document SHA-256 613171c8…adde9 is anchored in Sepolia transaction 0xeb912fd2…ed19, block 11,839,743. See section 13.
Production still on AnvilThe live site at the domain root still anchors to Anvil. The Sepolia deployment runs in parallel under /sepolia (UI) and /sepolia-api (API). No cutover has happened.

2. What PITS proves — and what it does not

The system can supportThe system does not support
The uploaded bytes are identical to bytes that were registered (SHA-256 match).That the content of the document is true, accurate or official.
A registered hash was written into a specific blockchain transaction, sent by the PITS wallet, in a specific block with a block timestamp.That the publisher who registered it was authorised to speak for the issuing organisation (that is an identity/organisational question handled in Keycloak, not on-chain).
The anchor can be checked independently of PITS with a public block explorer (public chains only).That a local Anvil anchor is independently checkable — Anvil is a private, resettable, in-memory chain.
Any single-byte change to the file breaks the match.That two documents that look alike (re-scanned, re-saved, compressed) match; they hash differently.
Wording used by the UI“This result only proves document integrity, not the truth of its content.” Papers and slides should keep that boundary.

3. Architecture

Design principles

  • Thin anchoring. No smart contract: the anchor is a plain self-transfer carrying the hash as calldata. This works on any EVM chain with no deployment step and no contract address to trust.
  • Hash only. Uploaded files are processed in memory and never written to disk or stored. The registry keeps the hash and metadata.
  • Configuration, not code, selects the chain. BLOCKCHAIN_RPC_URL, BLOCKCHAIN_PRIVATE_KEY and BLOCKCHAIN_CHAIN_ID decide where anchors go; the backend refuses to start if the RPC reports a different chain ID.
  • Public verification needs no account. POST /verify and GET /verify/{sha256} are unauthenticated; registration requires a Keycloak token with the publisher role.

5. Anchoring protocol

5.1 Hashing

The live endpoints compute SHA-256 over the raw uploaded bytes (hashlib.sha256(content).hexdigest(), 64 lowercase hex characters). The code base also contains a text canonicalisation helper (CRLF→LF, trailing-whitespace strip, UTF-8) used by unit tests, but it is not used by /register or /verify. A document is therefore identified by its exact bytes.

Consequence for the paperRe-saving or re-scanning a PDF changes its hash even if it looks identical. Only the original file verifies.

5.2 Transaction format (anchor_type = calldata-v1)

FieldValue
from / toThe PITS signer address (a self-transfer; no counterparty, no contract)
value0
data0x + hex of "VALUE:" + sha256_hex — 6 + 64 = 70 bytes
chainIdRead from the RPC; must equal BLOCKCHAIN_CHAIN_ID

input (utf-8 of calldata) = VALUE:613171c873064a79d01805ba70f1cb5f4460800e46e83b8728d6bbf32b6adde9

Records re-anchored after the Anvil reset use anchor_type = calldata-v1-reanchored (see section 15). The wire format is identical.

5.3 Gas and fees (no hard-coded values)

  • Gas limit = eth_estimateGas × 1.20 (20 % buffer against estimator variance between providers). Observed gas used for the canonical transaction: 23,800.
  • EIP-1559 fees: maxPriorityFeePerGas = eth_maxPriorityFeePerGas (fallback: median of eth_feeHistory rewards over 5 blocks); maxFeePerGas = 2 × current base fee + priority fee. A 2× base-fee multiple survives about six consecutive full blocks.
  • Balance pre-check: if the wallet cannot cover gas × maxFee, the API returns 503 Anchor wallet has insufficient funds and stores nothing.
  • Observed cost of the canonical anchor: 23,800 gas × 0.977322016 gwei = 0.0000232603 ETH (Sepolia test ETH, no monetary value).

5.4 Nonce safety

Concurrent registrations from one signer must not reuse a nonce. Three mechanisms, each added after a concrete failure:

  1. Pending nonce. eth_getTransactionCount(addr, "pending") instead of latest.
  2. Serialisation lock. Reading the nonce, signing and broadcasting run under a PostgreSQL transaction-scoped advisory lock (pg_advisory_xact_lock) keyed by sha256(chain_id:address) truncated to a signed 64-bit integer. The lock also protects several backend containers sharing one database. On SQLite (tests) a process-local lock is used.
  3. Nonce floor. Public RPC providers are load-balanced: right after a broadcast, pending may still be served by a node that has not seen the transaction. In the live rehearsal, 2 of 4 simultaneous registrations failed with replacement transaction underpriced although the lock worked. The last-used nonce per (chain, signer) is now stored in table anchor_signer_nonces and used as a floor for 120 s (the floor expires so a dropped transaction cannot create a permanent nonce gap). After the fix, 6 simultaneous registrations all succeeded with nonces 6–11.

5.5 Receipts and anchor lifecycle

  • The API waits at most BLOCKCHAIN_RECEIPT_TIMEOUT_SECONDS (default 45 s). If no receipt arrives it responds normally with anchor_status: "pending"; the record is confirmed later, the next time it is registered again or verified (a non-blocking receipt lookup).
  • BLOCKCHAIN_CONFIRMATIONS (default 1) sets how many blocks must include the transaction before confirmed.
  • Blocking chain calls run in a worker thread so they do not stall the event loop.
  • A failed anchor is re-broadcast if the same document is registered again.
  • Observed receipt latency on Sepolia: roughly 3–25 s (block time about 12 s); the canonical registration returned in 5 s.

6. Verification algorithm

verify(file or sha256):
  hash  = SHA-256(file bytes)                      # or the supplied hex
  rec   = registry_records WHERE content_hash = hash
  if no rec                       -> valid=false (not registered)
  if rec.chain_id != backend chain -> valid=false, status chain_not_available
  if rec.anchor_status == pending  -> refresh receipt once; still pending -> valid=false, status pending
  if rec.anchor_status == failed   -> valid=false, status anchor_failed
  tx = eth_getTransactionByHash(rec.transaction_hash)
       not found                   -> valid=false, status transaction_not_found
       not mined                   -> valid=false, status pending
       input not "VALUE:"+utf8     -> valid=false, status invalid_anchor_payload
  if tx.input value != rec.content_hash         -> status hash_mismatch
  if rec.anchor_wallet and tx.from != wallet    -> status wallet_mismatch
  else                                          -> valid=true,  status confirmed (+ block timestamp)
verification_statusMeaningvalid
confirmedHash matches a mined anchor sent by the recorded wallettrue
pendingRegistered, transaction not yet mined/confirmed. Never reported as valid.false
anchor_failedReceipt status 0false
transaction_not_foundThe record points to a transaction that no longer exists on its chainfalse
chain_not_availableRecord belongs to another chain than this backend is connected to (e.g. a legacy Anvil row seen from the Sepolia API)false
hash_mismatch, wallet_mismatch, invalid_anchor_payloadOn-chain data disagrees with the registryfalse

Anything other than a confirmed, matching anchor is returned as valid:false with an explicit status — never as an HTTP error — so a client cannot mistake “cannot verify here” for “verified”. A hash that was never registered returns {"valid": false, "content_hash": "…"} with no record ID.

Schema changes are explicit

Application start-up only checks the schema and refuses to run if it is out of date. Changing it is a deliberate deployment step: python -m trustmark.infra.schema check|migrate. On PostgreSQL migrate runs src/trustmark/migrations/*.sql in one transaction under an advisory lock (all-or-nothing, safe if two runners overlap, additive only). A test fails if the SQL files drift from the ORM models. SCHEMA_AUTO_APPLY=true exists for local/CI only.

Database separation

The Sepolia rehearsal uses its own database (trustmark_sepolia, pinned by REQUIRE_DATABASE_NAME so the process refuses to start against any other) because content_hash is globally unique and test chains must never mix with production records.

9. Authentication & authorisation

  • Identity provider: Keycloak 26, realm nextjs-kc. Self-registration and password reset are disabled; accounts are created by an administrator or through the optional Google identity provider. publisher is the realm’s default role.
  • Frontend login: OpenID Connect authorisation-code flow through Auth.js (confidential client nextjs-web). The access token is kept in an encrypted session cookie and refreshed with the refresh token; the browser never sees the token in JavaScript.
  • Backend validation (KeycloakVerifier): the bearer JWT is verified with RS256/PS256 against the realm’s JWKS (cached one hour, refreshed on unknown kid), checking iss and aud. Roles come from realm_access.roles and the client’s resource_access. require_roles("publisher") guards registration and listing.
  • Per-user isolation: GET /records filters on the token’s sub. Before 14 Sep 2026 this endpoint listed every user’s records (an IDOR finding); it was fixed and verified with two real accounts.
  • Issuer identity: the realm export originally defined no sub mapper, so tokens lacked sub and issuer_id was empty. A protocol mapper fixes this.
Known authentication riskThe backend entrypoint contains a TEST_MODE switch that, when set to true, replaces authentication with a hard-coded publisher. It is False in every deployed container (checked), but the mechanism still exists in code.

Public-chain verification UI (October 2026)

  • A shared Blockchain Proof component shows network, status, shortened transaction (full value in the tooltip and the copy button), block number and a “View on Etherscan” link.
  • Network name and explorer URL come only from the API (anchor.network_name, anchor.explorer_tx_url). The UI never builds an explorer URL; it accepts https: links only, opens them in a new tab with rel="noopener noreferrer", and shows none for the legacy Anvil chain.
  • States handled: confirmed, pending, failed, transaction not found, legacy/chain unavailable, mismatch, unknown status, and responses from older backends with no anchor at all.
  • Language: Indonesian and English dictionaries with a key-parity test.

Serving under a sub-path

Because the domain cannot get a new sub-domain, the rehearsal UI is built with basePath=/sepolia (NEXT_PUBLIC_BASE_PATH); the production build has none. Things Next.js does not prefix by itself were handled explicitly: raw fetch URLs, window.location, the next/image source, the Auth.js base path and redirect URIs, and Auth.js cookie names. Rehearsal cookies are named __Secure-sepolia.authjs.* with Path=/sepolia and the rehearsal has its own AUTH_SECRET, so a login on one app cannot overwrite or read the other’s session. A small banner (NEXT_PUBLIC_ENV_LABEL) marks the rehearsal as “Public Blockchain Rehearsal · Ethereum Sepolia”.

Deployment method (non-obvious, by necessity)

  • The production checkout on the server has diverged from Git, so nothing is deployed with git pull. Only the changed files are copied, checksummed, and the single affected service is rebuilt and recreated with --no-deps.
  • The rehearsal runs as separate Compose projects attached to the existing Docker network, so building or restarting them cannot recreate production containers.
  • The frontend is built off-server. A full next build run on the 4 GB host coincided with a hang of the whole machine (section 15). The rehearsal image therefore contains only the pre-built .next output (built on a developer laptop) plus npm ci --omit=dev. A runtime next.config.js supplies the base path, because next start reads it from the config file, not from the build output.
  • Secrets live only in server-side .env files (mode 600) and are never committed. The Sepolia signing key is a freshly generated wallet used for nothing else.

13.2 Behaviour proven on the live rehearsal

  • Duplicate registration returns the existing record without a second transaction.
  • Pending path: with the receipt timeout set to 1 s, registration returned pending with the transaction hash stored; verification reported valid:false / pending; a later verification reported valid:true / confirmed and the row became confirmed with its block number.
  • Unfunded wallet: 503, nothing stored.
  • Six simultaneous registrations: six HTTP 200, nonces 6–11, no broadcast failures (after the nonce-floor fix).

13.3 Legacy records

Production holds 57 registry records originally anchored on Anvil. After a reboot reset the in-memory chain to block 0, none of them could be verified (three had already been orphaned earlier the same way). They were restored in two independent ways, both labelled calldata-v1-reanchored and both keeping the original created_at:

  • On Sepolia (copied into the rehearsal database): 57 of 57 now verify as confirmed through the Sepolia API.
  • On Anvil (production): the 57 hashes were re-anchored on the live Anvil (blocks 9–65) and only the transaction_hash column in production was updated, with a full database dump taken first and an old→new mapping file kept. 57 of 57 now verify through the production API.
Timestamp caveat for the paperThe on-chain timestamp of a re-anchored record is the re-anchoring time (4 Oct 2026), not the original registration date (6–9 Sep 2026); the original date is only in the database. Re-anchoring proves the document existed unchanged at re-anchoring time, not at the original date.

16. Limitations & threat model

TopicStatus
Hash only, byte-exactBy design. Content truth, authorship of the content and semantic equivalence are out of scope.
Operator trustA single PITS wallet signs every anchor, and the registry lives in a database the operator controls. The on-chain record cannot be altered, but the registry could be edited to point elsewhere. Independent verification (section 17) removes that dependency because it recomputes the hash and checks the transaction sender directly.
Anyone can anchor any hashThe chain does not restrict who writes VALUE:…. Trust comes from the sender being the known PITS wallet, which a verifier must check. A contract-based registry (Registered(hash, publisher) events) would make this enforceable on-chain; it is a possible future work item.
Finality“Confirmed” currently means one confirmation (configurable). Reorg risk on a public chain is not modelled further.
TestnetSepolia is not economically secured; faucet ETH has no value. Production would need mainnet/rollup and a funded, protected key.
Key managementThe signing key sits in a server-side .env file. A KMS/HSM and balance alerts are not in place.
AvailabilityOne 4 GB VPS hosts everything (single point of failure); no automatic start of Docker/nginx after reboot; no background job to confirm pending anchors; verification depends on an RPC provider.
AuthenticationTEST_MODE bypass still present in code (off in deployments); no rate limiting on public endpoints; sign-up intentionally disabled.
PrivacyFiles are not stored, but file name, content type, publisher ID and hash are in the registry. The hash of a public document is public information on-chain.
Legacy re-anchoringTimestamps reflect re-anchoring time (section 13.3).
Performance claimsHistorical load-test figures from before the fixes were produced with a test harness that had defects (missing Authorization header; an always-true type check). They should not be compared with new measurements and are not part of this documentation.

17. Independent verification recipe

Anyone can verify a Sepolia-anchored PITS document without trusting PITS:

  1. Compute the SHA-256 of the file: shasum -a 256 document.pdf.
  2. Obtain the transaction hash (shown by the PITS UI, or from GET /sepolia-api/api/v1/verify/<sha256>).
  3. Open https://sepolia.etherscan.io/tx/<hash>. Check: status Success; From equals To equals the published PITS wallet 0x3EB7D8332a8405a81Dbae7Bc2dA2FAfAe3603EB5; value 0.
  4. Expand More details → Input data, switch to UTF-8: it must read VALUE: followed by your SHA-256.
  5. The block timestamp is the earliest time the hash was provably public (for re-anchored legacy records: the re-anchoring time).

18. Glossary

Anchor
A blockchain transaction that carries a document hash, making the hash’s existence at that time publicly checkable.
Calldata
The data/input field of an Ethereum transaction. Here: VALUE:<sha256>.
Anvil
Foundry’s local Ethereum node for development; chain ID 31337.
Sepolia
A public Ethereum test network; chain ID 11155111.
EIP-1559
Ethereum fee market with a base fee and a priority tip.
Nonce
Per-account transaction counter; each transaction needs the next unused value.
Advisory lock
PostgreSQL application-level lock, here used to serialise nonce selection per signer.
JWKS
JSON Web Key Set: the public keys used to verify Keycloak-issued JWTs.
RPC provider
Service exposing an Ethereum node over JSON-RPC.
Re-anchoring
Writing an existing record’s hash to a (new) chain again after its original proof was lost.
