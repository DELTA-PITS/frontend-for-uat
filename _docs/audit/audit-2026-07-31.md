# Audit Codebase — Frontend PITS (`frontend-for-uat`)

**Tanggal audit**: 2026-07-31
**Lokasi**: `frontend-for-uat/`
**Konteks project**: Aplikasi Next.js App Router "Public Information Trust System (PITS)" dengan 2 portal (Publisher & Verification), auth via Keycloak/NextAuth, styling TailwindCSS + daisyUI, linting via Oxlint, testing via Jest + Vitest + Storybook.

## 1. Struktur & Arsitektur

### Duplikasi total component tree (High)

Ada dua struktur folder component hidup berdampingan dan **tidak sinkron**:

- **Aktif** (dipakai nyata oleh `app/`, `hooks/`, `stories/`, `components/index.ts`): `components/BgHeader.tsx`, `FileUpload.tsx`, `ResultView.tsx`, `api.ts`, `auth/{SignIn,SignOut}.tsx`, `common/{DocumentPreview,Dropzone,FilledIcon,LoadingCard,OperationButton,OperationCard,SummaryRow}.tsx`, `layout/Header.tsx`
- **Mati, tidak diimpor dari manapun di luar dirinya sendiri**: `components/features/auth/{SignIn,SignOut}.tsx`, `features/result/{BgHeader,LoadingCard,ResultView}.tsx`, `features/upload/{DocumentPreview,Dropzone,FileUpload,api,index}.ts(x)`, `ui/{FilledIcon,OperationButton,OperationCard,SummaryRow}.tsx`

Dibuktikan via grep menyeluruh `from '@/components\|@components'` di `app/`, `hooks/`, `stories/`, `components/` — tidak ada referensi ke `features/*`/`ui/*` dari kode yang benar-benar dieksekusi.

README.md sendiri mendeskripsikan struktur `features/`/`ui/` sebagai struktur **resmi** — jadi ini migrasi refactor yang **ditinggal setengah jalan**: 15 file dead code tidak pernah dihapus, dan sudah **divergen** dari versi aktif (dikonfirmasi via `diff`, bukan sekadar salinan identik):
- `BgHeader.tsx`, `FileUpload.tsx`, `auth/SignIn.tsx`, `auth/SignOut.tsx`, dan semua `common/*` vs `ui/`/`features/` — **berbeda**
- Hanya `ResultView.tsx` dan `api.ts` yang identik dengan pasangannya.

**Risiko**: developer baru yang mengikuti struktur README akan mengedit file yang tidak pernah dirender, menghabiskan waktu debug tanpa hasil.

**Rekomendasi**: hapus seluruh `components/features/` dan `components/ui/`, atau selesaikan migrasi (hapus struktur lama, update semua import) — pilih satu, jangan biarkan berdampingan.

### Route orphan
`app/verify/page.tsx` hanya placeholder statis ("Welcome to the Verification Page...") — tidak terhubung dari navigasi manapun (`components/layout/Header.tsx:22-33` hanya menautkan `/`, `/dashboard`, `/publisher`). Fungsi verifikasi sesungguhnya ada di `app/page.tsx` (root `/`).

## 2. Security

### Auth (`auth.ts`) — NextAuth v5 (beta) + Keycloak
- `next-auth@5.0.0-beta.31` (**Medium**) — masih prerelease sebagai fondasi auth produksi; API bisa berubah tanpa semver stabil.
- `refreshAccessToken` (`auth.ts:7-56`) menangani refresh token dengan baik: semua error-path di-catch, mengembalikan token dengan flag `error` alih-alih throw — pola aman, tidak membocorkan detail error ke client.
- `authorized` callback (`auth.ts:62-65`) hanya melindungi `/publisher` dan `/dashboard`. Route API (`/api/register`, `/api/records`) tidak dilindungi middleware — proteksi terjadi manual di masing-masing route handler via `await auth()`. **Medium** — defense-in-depth gap: kalau ada route API baru dan developer lupa memanggil `auth()` manual, tidak ada fallback proteksi.
- `proxy.ts` (Next.js middleware, `export { auth as proxy }`) matcher mencakup semua path termasuk `/api/*`, tapi karena `authorized()` return `true` untuk path selain `/publisher`/`/dashboard`, middleware efektif tidak melakukan apa-apa untuk API routes. Tidak ditemukan SSRF/request-forwarding tidak aman — file ini minim, hanya re-export.

### Dual env var Keycloak (Medium)
- Server-side (`auth.ts:13-15`): `AUTH_KEYCLOAK_ISSUER`, `AUTH_KEYCLOAK_ID`, `AUTH_KEYCLOAK_SECRET`.
- Client-side (`components/auth/SignOut.tsx:9-10,39`, duplikat di `components/features/auth/SignOut.tsx`): `NEXT_PUBLIC_AUTH_KEYCLOAK_ID`, `NEXT_PUBLIC_AUTH_KEYCLOAK_ISSUER`, `NEXT_PUBLIC_AUTH_URL`.

Client ID/issuer Keycloak harus dikonfigurasi dua kali per environment — risiko config drift nyata (client ID bukan rahasia, tapi maintenance risk tetap ada).

Bug fungsional terkait: `generateKeycloakLogoutUrl` dipanggil tanpa `idToken` (`SignOut.tsx:38-40`) — parameter kedua tidak pernah di-pass dari manapun. Kemungkinan Keycloak logout menampilkan halaman konfirmasi manual alih-alih silent logout (UX bug).

### Tidak ada validasi upload file (High)
- `app/api/_lib/parseUpload.ts:1-9` hanya cek `file instanceof File` dan `filename` string — **tidak ada validasi ukuran, tipe MIME, atau ekstensi**. File apa pun diteruskan mentah ke backend (`app/api/register/route.ts:30-41`, `app/api/verify/route.ts:20-23`).
- `components/common/Dropzone.tsx:27` — `useDropzone({ onDrop })` dipanggil tanpa opsi `accept`/`maxSize` (react-dropzone punya dukungan bawaan, tidak dimanfaatkan).
- Semua validasi didelegasikan ke backend eksternal — user baru tahu file ditolak setelah round-trip penuh.

### Payload sensitif di URL query string (Medium)
`lib/resultPayload.ts:6-8` — `buildResultHref` men-serialize seluruh `ResultPayload` (content hash, record ID, transaction hash, issuer ID, filename, pesan error backend) jadi JSON di query param `payload`, dipush via `router.push` (`hooks/useUpload.ts:76,90`). Masuk ke browser history, berpotensi muncul di access log reverse-proxy/CDN, bisa ter-share tanpa sengaja lewat URL. Tidak ada penanganan batas ukuran URL jika pesan error backend panjang.

### Default issuer ID hardcoded (Low-Medium)
`app/api/register/route.ts:6` — `DEFAULT_ISSUER_ID` hardcoded sebagai fallback saat `PITS_ISSUER_ID` env var tidak diset (baris 26). Bukan secret, tapi kesalahan konfigurasi (lupa set env) di production akan **diam-diam** mendaftarkan semua dokumen di bawah issuer yang salah — silent failure berbahaya untuk sistem trust dokumen.

### Lain-lain
- Tidak ditemukan hardcoded password/secret/token literal, `dangerouslySetInnerHTML`, atau `eval()`.
- Tidak ada `.env.example` di root — env var (11 nama berbeda) tersebar tanpa referensi terpusat (**Low**, DX/onboarding, tapi meningkatkan risiko misconfigurasi seperti item issuer di atas).
- `.gitignore` mencakup `.env*` dengan benar.

## 3. Testing (High)

- **`jest.config.ts`** (677 baris, mayoritas komentar boilerplate default) — `testEnvironment` tidak diset (default `"node"`), padahal `jest-environment-jsdom` ada di devDependencies. **Tidak ada satupun file test** di seluruh repo (`*.test.ts*`/`*.spec.ts*` nol hasil) — `npm test` akan gagal "no tests found".
- **`vitest.config.ts`** bukan unit-test runner independen — hanya dipakai untuk Storybook interaction test via `@storybook/addon-vitest`. Tidak punya npm script sendiri.
- **Kesimpulan**: `jest.config.ts` adalah leftover scaffold tidak terpakai dan salah konfigurasi; `vitest.config.ts` satu-satunya test runner yang wired, tapi cakupannya terbatas story-based test, bukan unit test business logic (`lib/*.ts`, `hooks/useUpload.ts` — nol coverage).

### Storybook
11 file `.stories.tsx`, semua mengimpor dari struktur lama (konsisten dengan komponen aktif — poin bagus). Cakupan terbatas pada komponen presentasional (`common/`) + 3 komponen page-level. Tidak ada story untuk `layout/Header.tsx`, `auth/{SignIn,SignOut}.tsx`, `app/dashboard/page.tsx`, `app/verify/page.tsx`.

## 4. Type Safety

- `tsconfig.json` — `"strict": true` aktif. Baik.
- `types/` rapi: `api.types.ts`, `files.types.ts`, `next-auth.d.ts` (module augmentation Session/JWT — pola benar), `index.ts` barrel export. Tidak ada `any` berlebihan.
- Satu-satunya `any` eksplisit: `fileRejections: any[]` di kedua copy Dropzone (`common/Dropzone.tsx:17`, `features/upload/Dropzone.tsx:16`) — seharusnya pakai tipe resmi `FileRejection[]` dari react-dropzone. **Low.**

## 5. Performance & Next.js Best Practice

- `'use client'` di 15 dari 43 file (~35%). `app/dashboard/page.tsx` (`'use client'`) melakukan data fetching (`fetch('/api/records')` di `useEffect:18-26`) yang seharusnya di server component — pola client-fetch-on-mount klasik menyebabkan waterfall.
- `<img>` biasa dipakai bukan `next/image` di `components/BgHeader.tsx:17` (dan duplikat `features/result/BgHeader.tsx:15`) — kontras dengan `layout/Header.tsx:76` yang sudah benar memakai `<Image>` — inkonsistensi dalam codebase yang sama.
- `useEffect` + `isMounted` pattern di `components/FileUpload.tsx:46-50` untuk hindari hydration mismatch tooltip — indikasi state/markup berbeda server vs client render, worth diperiksa apakah bisa dibuat SSR-safe.

## Rekomendasi Tindak Lanjut (urutan prioritas)

1. Putuskan dan selesaikan migrasi component tree: hapus `components/features/`+`components/ui/` ATAU selesaikan migrasi dan hapus struktur lama — jangan biarkan dua versi berdampingan dan divergen.
2. Tambahkan validasi file upload (tipe MIME, ekstensi, ukuran) di client (`Dropzone` `accept`/`maxSize`) dan server (`parseUpload.ts`).
3. Bersihkan setup test: hapus `jest.config.ts` yang tidak terpakai (atau perbaiki `testEnvironment`), tulis unit test untuk `lib/*.ts` dan `hooks/useUpload.ts` via Vitest.
4. Aktifkan kembali CI linting sebelum lanjut dari UAT ke tahap berikutnya; sinkronkan README/CONTRIBUTE.md dengan state repo aktual.
5. Evaluasi upgrade `next-auth` ke versi stabil begitu tersedia; tambahkan proteksi middleware (defense-in-depth) untuk route API.
6. Hindari menaruh data hasil (hash, record ID) di query string — pertimbangkan session storage / server state / route param berbasis ID pendek yang di-resolve server-side.
7. Buat `.env.example` yang mendokumentasikan seluruh env var yang dibutuhkan.
8. Hapus dependency tak terpakai (`lucide-react`), ganti `any[]` di Dropzone dengan `FileRejection[]`, hapus `console.log` debug.
