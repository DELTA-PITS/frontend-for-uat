1. Purpose and Intended Use

This document explains how PITS was independently tested, why multiple test layers were used, how evidence was classified, and how the resulting evidence should be interpreted by the paper author. It is not a claim that PITS is production-certified, and it is not a penetration-test report.

Author-facing purpose. The package is designed so the paper author can write the Methodology, Evaluation, Results, Discussion, and Limitations sections without having to infer test meaning from source code or terminal logs.

2. System Under Test

PITS (Public Information Trust System) is a proof-of-concept verification architecture for public digital documents. The implemented flow is: authenticated publisher registration → SHA-256 of uploaded bytes → PostgreSQL registry record → Ethereum-compatible Anvil transaction carrying the hash → public verification without login.

Publisher Portal

Protected registration and registration-history workflows.

Verification Portal

Public document/hash verification without authentication.

Backend

FastAPI, SQLAlchemy, Keycloak JWT verification, SHA-256, Web3.

4. QA Roles and Use of AI

Laksa Ersa acted as the developer/technical contributor directing the independent QA work. Claude Code was used as an AI coding agent to read source, design test cases, write test code, execute real commands, inspect actual outputs, and document findings. It must not be described as an independent human reviewer.

Important distinction: test design was AI-assisted under human direction, but reported runtime results came from actual subprocess execution, HTTP calls, database operations, browser automation, and local infrastructure—not generated or simulated numbers.

6. Testing Approach

Unit testing

Isolated backend/frontend behavior. Backend mocked external infrastructure; frontend used Vitest/jsdom. Some tests intentionally assert known broken behavior so a PASS can mean “the defect was reproduced.”

API E2E

Real HTTP requests against the deployed backend to exercise registration, duplicates, authentication/authorization and verification.

Browser E2E

Playwright drove real user journeys through login, registration, public verification, edge cases, session/result-state and responsive checks.

Source audit

Backend and frontend source were read systematically to confirm implementation paths, dead code, configuration risks and root causes.

Full-stack integration

Final disposable local stack: real Postgres, Keycloak, Anvil and FastAPI. Two publishers plus a no-role account enabled direct tenant-isolation tests.

Performance / reproducibility

Locust was corrected, rerun 3×60 seconds at 10 users, and raw CSV/HTML/log artifacts were retained.

8. Pass / Fail / Blocked Rules

  • PASS: executed and actual behavior matched the stated expected behavior.
  • FAIL: executed and actual behavior did not match expected behavior; may indicate a product defect.
  • SKIP / BLOCKED / XFAIL: not fully executed because a documented precondition/environment was unavailable or intentionally excluded.
  • INCONCLUSIVE: execution occurred but evidence was insufficient to attribute the failure to the application.
Do not aggregate blindly. A unit test that intentionally asserts a known defect can pass while the application remains broken. The paper should report outcomes by evidence layer and objective, not a single “overall pass rate.”

9. Safety and Production Constraints

Earlier live E2E work was authorized when the deployed environment had no real end users, but it still contained accumulated test records and shared-server services. The final integration pass therefore used a fully disposable local replica and did not touch production. Destructive resilience actions were restricted to local containers.

11. Methodological Limitations

  • No claim of formal penetration testing or production certification.
  • Historical live Playwright/API results were not all rerun on 14 Sep 2026.
  • True validly-signed wrong-issuer/audience JWT tests still need a second signing realm.
  • Pending Anvil transaction state was not reproducible under instant auto-mining.
  • Accessibility, real-device testing, full DR/backup-restore and capacity-to-failure stress testing remain outside the final evidence set.
  • Historical performance figures in the paper cannot be reconstructed exactly because raw artifacts and exact historical configuration are unavailable.
