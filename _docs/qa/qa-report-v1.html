01

Scope & Method

This pass complements, rather than replaces, the testing already described in the paper. It targets exactly the paths the paper claims are covered — registration, duplicate detection, authentication failure, and verification — and runs them as reproducible, automated code against the real production deployment instead of one-off manual checks.

Who ran this

AI coding agents (Claude), supervised

Test design, implementation, execution, and triage were performed by AI agents working against the live server, with a human (Laksa Ersa, the team's engineer — not a paper author) reviewing and directing the work. No paper author or the PITS developer was involved in writing these tests.

Where

Live production, not a local sandbox

All tests hit pits.pangkalandata.id and pits-ui.pangkalandata.id directly — the same deployment referenced in the paper's evaluation, not an isolated Docker Compose environment.

Constraints

One test account, HTTP-only

Only one publisher credential (uat-tester) was available, and no SSH or database access was used. Two scenario classes could not be empirically completed as a result — documented in Section 5, not silently skipped.

03

Findings

Four issues were confirmed against production. The first two are the ones that matter most for the paper's claims about source verification and access control.

CriticalFinding 1 — AUTH-7

Any publisher can read every other publisher's registration history

GET /api/v1/records (documents.py::list_records) queries the registry with no issuer_id filter at all:

records = db.query(RegistryRecord).order_by(RegistryRecord.created_at.desc()).all()

Confirmed two independent ways: by code inspection (the query structurally cannot exclude anyone), and empirically — the uat-tester account, created 2026-09-07, retrieved documents filed under filenames such as "cv E. Indarto 2020 - EN.pdf" and "Resume (1).pdf" dated 2026-09-06, before that account existed. It could not have registered them.

Impact

Every publisher's filing history — filenames, timestamps, hashes — is visible to every other publisher through one ordinary authenticated call. This is an access-control gap between tenants, not a hypothetical one.

CriticalFinding 2 — REG-1 / systemic

Every registered document has lost its publisher identity

The production Keycloak access token issued to uat-tester carries no sub claim — the standard OIDC subject identifier that Keycloak includes by default. Decoded directly from the JWT payload, the claim set has iss, aud, preferred_username, and a dozen others, but no sub.

Principal(sub=claims.get("sub", ""), ...) → issuer_id = ""

Checked against the full production table: 42 of 42 records — not just this session's — have issuer_id: "". This is very likely the root technical cause behind the paper's own §5.1 caveat ("the live registration response contained an empty issuer_id") — and it means the source-verification function in Table 1 of the paper (associating a document with an authorised publisher) is not currently satisfied in production, regardless of how well the registration flow itself works.

Likely cause

A missing or removed sub protocol mapper on the nextjs-web client scope in the nextjs-kc realm. Worth fixing before the fix for Finding 1 — a per-publisher filter is meaningless while every publisher's identity resolves to the same empty string.

MediumFinding 3 — AUTH-2

A malformed bearer token crashes the endpoint instead of being rejected

Sending Authorization: Bearer garbage-string to /api/v1/register returns 500 Internal Server Error, not the 401 every other invalid-token case returns. KeycloakVerifier.verify() calls jwt.get_unverified_header(token) before any try/except is in scope; a string that isn't a JWT at all raises unhandled.

Fix

Wrap that call the same way jwt.decode() already is, and return 401.

MediumFinding 4 — REG-3 / REG-4 / TC-11b

The app's 20MB upload limit is never actually reachable

The app is configured for MAX_UPLOAD_BYTES=20MB, but nginx in front of it enforces its own default client_max_body_size (~1MiB). A binary search against production found the real cutoff at exactly 1,048,403 bytes — anything larger gets a bare nginx HTML error page, not the app's JSON error. A normal multi-page scanned PDF (often >1MB) will fail to register with a confusing, unbranded error.

Separately, no file-type or magic-byte validation exists at all — a text file renamed to .pdf is accepted and registered by the API (confirmed from both the backend suite and, independently, the frontend suite bypassing the UI entirely).

Fix

Raise nginx's client_max_body_size to match the app config; add a PDF magic-byte check (%PDF- header) server-side, since client-side filtering alone is bypassable.

No bug foundDUP-4

Concurrent duplicate registration does not create a race

Two simultaneous register requests for byte-identical content produced exactly one blockchain transaction, with the second request correctly resolving to already_existed: true. No 500, no duplicate transaction, no orphaned record. This one held up.

Not Yet Tested

Documented gaps, not silent ones — each of these was deliberately left out of this pass, and why.

Blocked by test account

DUP-2, AUTH-4, full AUTH-7 proof

Need a second publisher account (or one without the publisher role). Only uat-tester was available; creating a new Keycloak user was outside this session's permissions.

Blocked by access level

VER-7, VER-8

On-chain/registry desync and a downed blockchain node both require direct SSH or Anvil access to simulate — out of scope for an HTTP-only test session.

Out of session scope

Load re-verification, deep security testing

Locust load numbers in the paper were not re-run this session. No fuzzing, brute-force/rate-limit testing, CSRF, dependency scanning, or infrastructure-level penetration testing was attempted.

Out of session scope

Cross-browser, disaster recovery, human evaluation

Only Chromium was tested (no Safari/Firefox, no real mobile device). No DB/Anvil backup-restore drill. §5.5's Public User Evaluation is a human study — it is not something this kind of testing can substitute for.

Unit Test Coverage Review

The 17 existing unit tests cover 2 of 29 backend source files — both low-risk. The two modules that actually hold Findings 1–3 have zero isolated test coverage. Below is a full review of what's testable in each, mocked and fast (milliseconds, no live server), that would have caught both critical findings without ever touching production.

Why this matters for the paper specifically: a mocked unit test for list_records() with two records under two different issuer_id values proves Finding 1 in isolation, deterministically, and can run in CI on every commit — stronger evidence than a one-time live-server observation, and exactly the kind of reproducible artefact a reviewer would expect next to a 100%-pass claim.

Recommendations

Fix, in order

1. Restore the sub claim, then filter records

Fixing Finding 1 (add an issuer_id filter) before Finding 2 (missing sub) is fixed will not work — every publisher would still resolve to the same empty identity.

Fix

2. Wrap the token-parsing call in keycloak.py

Cheap, low-risk fix for Finding 3 — bring malformed-token handling in line with every other invalid-token path, which already return 401 correctly.

Fix

3. Align nginx's body-size limit with the app's

And add a server-side PDF magic-byte check — client-side filtering alone was proven bypassable (TC-17b).

Build

4. The 65 proposed unit tests in Section 6

Cheapest, fastest way to convert this session's live findings into permanent, CI-checkable regression coverage — and the most direct way to firm up the paper's requirement-traceability table (Table 3).
